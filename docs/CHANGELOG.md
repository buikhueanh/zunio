# Changelog

Running log of bugs encountered during development and how they were fixed.
Append-only, terse, dated. Architecture/product decisions live in
`info/DECISIONS.md` instead — this file is debugging history only.

## 2026-07-09

- **`npx ts-node supabase/seed.ts` failed with an ESM/CommonJS detection error.** → Root tsconfig targets `esnext` for Next.js, which made `ts-node` misdetect the seed script as an ES module when run directly. → Added `supabase/tsconfig.seed.json` forcing `commonjs`, run via `npm run seed` with `--project`.
- **Seed script env vars weren't loading (`Missing NEXT_PUBLIC_SUPABASE_URL`).** → `dotenv/config` only auto-loads `.env`, not `.env.local`. → Switched to `config({ path: '.env.local' })` explicitly in `supabase/seed.ts`.
- **Seed script crashed with `__dirname is not defined in ES module scope`.** → Same ESM detection issue reaching the file-path resolution code. → Replaced `__dirname` with `process.cwd()`-relative paths.
- **`npm run seed` failed with a JSON parse error from ts-node's arg parser.** → npm strips/mangles quotes when passing inline `--compiler-options '{"module":"commonjs"}'` through a package.json script. → Moved the override into `supabase/tsconfig.seed.json` and referenced it via `--project` instead of inline JSON.
- **`npm run build` failed with `Missing API key. Pass it to the constructor new Resend("re_123")`.** → `lib/resend.ts` instantiated `new Resend(...)` at module load time, which throws during build/prerender if `RESEND_API_KEY` isn't set yet (it wasn't, at that point). → Moved the `Resend` instantiation inside `sendWaitlistConfirmation()` so it's only constructed at request time.
- **Waitlist confirmation emails not sending (403 from Resend).** → `lib/resend.ts`'s `from` address (`hello@zunio.app`) is not a verified sending domain in Resend yet. → Not yet fixed — real domain still needs to be purchased and verified at resend.com/domains before launch (tracked as BUILDORDER item 0.9b/0.10 blocker). Confirmed the send pipeline itself works correctly via Resend's sandbox sender (`onboarding@resend.dev`).
- **Selecting a school in the combobox fired a wasted extra Supabase search.** → `components/ui/SchoolCombobox.tsx`'s debounce `useEffect` re-ran whenever `query` changed, including the change triggered by `selectSchool()` setting `query` to the formatted label — searching for a full "School Name — City, State" string that never matches anything. → Added a `skipNextSearch` ref that `selectSchool()` sets before updating `query`, so the effect skips that one re-run.
- **`rm -rf .next` while `next dev` was still running corrupted the webpack module cache**, causing `Cannot find module './948.js'` and similar errors on page load. → Multiple `next dev` processes (an old preview session that hadn't actually died, plus a new one) were writing to the same `.next` directory concurrently. → Killed all stray `next dev`/`next-server` processes for the project, cleared `.next` only once nothing was running, then started a single fresh dev server. General rule going forward: never run `next build` or delete `.next` while a dev server for the same project is live.

## 2026-07-23

- **Sign-up would have violated the `users.school_id` FK constraint for every user.** → Sign-up form initially reused `SchoolCombobox` (searches `schools_directory`, ~2,510 rows) as BUILDORDER item 0.6 specified, but `users.school_id` FKs to `schools` (active/launched only, currently 1 row) — a different UUID space. → Built a separate `ActiveSchoolSelect` component (`components/ui/ActiveSchoolSelect.tsx`) querying `schools` directly. Confirmed the fix with a real insert against the live FK constraint (201 Created) before shipping. See DECISIONS.md for the full writeup.
- **`/api/auth/sign-up` returned bare 500s with no way to diagnose the cause.** → Route caught Supabase Auth/DB errors and returned a generic message without logging the underlying error anywhere. → Temporarily added `console.error` around both error paths to diagnose (found real causes: `email_address_invalid` for `@example.com`, then `over_email_send_rate_limit` from Supabase's default mailer), removed the debug logging once resolved. Not a bug in the route itself — the underlying errors were real Supabase Auth behavior (RFC-reserved example domains rejected; free-tier mailer has a strict send-rate limit). Verified the DB insert path separately via the Admin API, which bypasses the mailer entirely.

## 2026-08-07

- **Seven tables were fully open to anonymous read AND write.** → `schools`, `schools_directory`, `messages`, `conversations`, `conversation_participants`, `blocked_users`, and `listing_matches` were created (migrations 001/002/004) without `ENABLE ROW LEVEL SECURITY`. With RLS off, Supabase's default grants let any holder of the public anon key — which ships in the site's JS bundle — read and modify them. Verified live against production: an anonymous `INSERT` into `schools_directory` returned `201` and an anonymous `DELETE` returned `204`. A single unauthenticated request could have wiped all 2,510 schools, instantly breaking sign-up and the waitlist school pickers. Surfaced by Supabase's own Security Advisor (7 "RLS Disabled in Public" errors) while auditing for a *different* issue. → Migration `008_rls_security_fix.sql`: enabled RLS on all seven; added SELECT-only policies to `schools`/`schools_directory` (the school pickers query these from the browser, so reads must stay open, but writes now only happen server-side via the service role); enabled RLS with no policies on the five v2 tables (chat/blocking/matching), so private DMs aren't world-readable the day chat ships. Re-verified after: anonymous INSERT now `42501 violates row-level security policy`, anonymous DELETE affects zero rows, school pickers still functional.
- **`users.contact_email` was readable by anyone with the public anon key.** → RLS filters *rows*, not *columns*, so the otherwise-correct "public read user profiles" policy exposed every column of every visible user, including real student email addresses — harvestable in one unauthenticated request. For a product whose pitch is verified student identity, that's both a privacy breach and a ready-made targeted phishing list. `contact_email` is explicitly meant to be private by design (`CLAUDE.md` specifies Resend relays messages server-side so buyers never see the seller's address). → **First attempt (migration 008) silently failed**: `REVOKE SELECT (contact_email) ON users FROM anon, authenticated` is a no-op in Postgres when the role already holds *table-level* SELECT — a table-wide grant implies all columns and a column-level revoke can't carve an exception from it. Caught by re-running the attack after applying, rather than assuming the migration worked. → Fixed properly in `009_hide_contact_email.sql` using the inverse pattern: `REVOKE SELECT ON users` (table-wide), then `GRANT SELECT (...)` listing only the safe columns. Deliberately kept public: `is_seller_verified` (wanted for a verified-student badge), `email_verified_at` (read by `EmailVerificationBanner` through the anon client — revoking it would have broken the banner, confirmed by grepping usage *before* writing the migration), and `is_suspended`/`deleted_at` (always false/null for RLS-visible rows). Verified after: `select=*` and any query naming `contact_email` both return `42501 permission denied`, while the banner's, middleware's, and the future profile page's exact queries all still succeed.

## 2026-10-01

- **`npm run build` failed, so no deploy could have succeeded.** → `components/forms/SignUpForm.tsx` still imported `useRef` after the username auto-fill work stopped using it. `next build` runs ESLint and treats `@typescript-eslint/no-unused-vars` as an error, so compilation succeeded and then the lint step aborted the build. `tsc --noEmit` passes on an unused import, which is why it went unnoticed locally — typecheck is not a substitute for a real build. → Removed the import; `npm run build` now completes and emits all 22 routes. Run `npm run build` (not just typecheck) before any deploy.

## 2026-08-19

- **The header linked to `/account`, which did not exist, and nothing anywhere could sign out.** → The browse header shipped an "Account" link while account settings (item 2.6) was still unbuilt, so it 404'd; only `/account/add-school-email` existed under that path. Worse, there was no sign-out control anywhere in the app, so a signed-in user could not get back to the logged-out view at all — which also blocked testing the marketing hero, since that only renders when logged out. → Added a minimal `app/account/page.tsx`: read-only profile summary, seller-verification status with the right next step, and a sign-out button. Full editing stays item 2.6. The page reads `contact_email` with the service role, per migration 009's note that a user's own address must be served server-side rather than by re-granting the revoked column.
- **Sign-in silently did nothing; the submit button stayed disabled.** → Not an app bug. The dev server had been running for hours across many edits and its webpack chunks went stale, producing `ChunkLoadError: Loading chunk app/(auth)/sign-in/page failed (timeout)`. Hydration then failed, React never attached its handlers, so the controlled inputs never updated state and `canSubmit` stayed false — the form looked fine and was inert. Credentials were verified good against Supabase directly, which is what ruled out the app. → Killed the stale `next dev` processes for this project only (four unrelated processes belonged to `~/ereworld`), cleared `.next` with nothing running, and started one fresh server. Same failure mode as 2026-07-09: when a page mysteriously stops responding to input in dev, check for ChunkLoadError before debugging the component.

- **A dropped websocket silently left chat threads missing messages.** → `MessageThread` subscribed once and appended only what arrived over the socket. Any disconnection — laptop sleep, wifi change, backgrounded tab — meant messages sent during the gap were never rendered, and supabase-js reconnects automatically, so the thread looked live and current while being quietly incomplete. Nothing told the user they were reading a stale conversation. → The subscribe callback now backfills from the database on `SUBSCRIBED`, which fires on the initial connect *and* after every automatic reconnect; results merge by id and re-sort, so replays and optimistic sends can't duplicate.
- **Chat would stop delivering after about an hour, with no visible failure.** → `realtime.setAuth()` was called once at subscribe time with the current access token. Supabase access tokens expire (~1h) and supabase-js refreshes them in the background, but the already-open socket kept the stale one — and since the channel stays `SUBSCRIBED`, delivery just stops without an error anywhere. → Added an `onAuthStateChange` listener that re-calls `realtime.setAuth()` on `TOKEN_REFRESHED`, with the subscription torn down on unmount.

- **Students whose school hosts mail on a subdomain could never become sellers.** → `verify-email` compared `emailDomain === schoolDomain` exactly. `schools_directory.domain` comes from IPEDS `WEBADDR` — the school's *website* domain — while student mail frequently lives on a subdomain (University of Cincinnati's site is `uc.edu`, student mail is `@mail.uc.edu`; Harvard uses `@g.harvard.edu`). Those students verified their email, stayed `is_seller_verified = false`, and were shown "Add a school email to post listings" — after adding exactly that. Silent *and* self-contradictory. Confirmed against the live waitlist, which already contains a `mail.uc.edu` signup. → Extracted the rule into `lib/school-email.ts`: exact match OR strict subdomain. **The dot boundary is load-bearing** — a plain `endsWith('uc.edu')` would have verified `buc.edu` students as University of Cincinnati, and `uc.edu`, `buc.edu`, `puc.edu`, `luc.edu` and `huc.edu` are all separate real institutions in the directory. Also added `schools.email_domains` (migration 016) as an *additive* allowlist for schools whose mail domain isn't derivable from their website domain, plus a `console.warn` on every near-miss so such schools are discoverable instead of silently blocking their students. Banner copy now says "verify an email that matches your school's domain" rather than implying they never added one. Covered by 31 assertions including lookalike domains (`evil-northeastern.edu`, `northeastern.edu.evil.com`), single-label blanket-match attempts, and malformed input.

- **A failed profile insert during sign-up left an orphaned auth account.** → `/api/auth/sign-up` creates the Supabase Auth user first, then inserts the `users` profile row. If that second step failed, the route returned 500 and walked away — leaving an auth account with no profile: the person could sign in but had no profile anywhere, and could not sign up again because the email was now taken (409). A permanently stuck account with no self-service recovery. Surfaced while adding username uniqueness, which introduces a *likely* failure for that insert (someone claiming the username mid-request) rather than a rare one. → The route now deletes the auth user when the profile insert fails, so a retry actually works, and logs loudly if that cleanup itself fails. Unique violations (23505) return a specific 409 "that username was just taken" rather than a generic 500. Verified: a duplicate-username sign-up returns 409 and leaves no auth user behind.

- **A listing could be in the `free` category and still have a price.** → Nothing tied the two representations of "free" together: `category = 'free'` and `price IS NULL` were independent, so `category='free', price=50` was accepted. That listing would appear under the Free *category* filter but be excluded from the "Free items" *price* filter, which keys off `price IS NULL` — the same listing free by one definition and not the other. → `listingSchema` now ends with a transform forcing `price = null` whenever the category is `free`. The implication is deliberately one-way: a giveaway in another category (a free textbook) keeps its category and stays valid. The form mirrors this — picking Free auto-ticks and disables the free checkbox, hides the price input, and explains why, so the price is never silently discarded behind the seller's back.
- **Enum inputs were case-sensitive, so `"Free"` was rejected as invalid.** → `category`/`condition` were validated with a bare `z.enum()` against lowercase values matching the DB CHECK constraints. Anything sent through the API directly with different casing or stray whitespace (`"Free"`, `"FREE"`, `" fRee "`, `"LIKE_NEW"`) failed with an opaque `Invalid listing` 400 for what is only a casing difference. The UI's `<select>` always sent canonical values, so this was invisible from the app and would only have surfaced via the API. → Added a `normalizeEnumInput` preprocess (trim + lowercase, non-strings passed through so real type errors still report correctly) on both fields, and applied the same canonicalization to the read side in `lib/listings.ts` — a mis-cased category filter previously matched zero rows silently rather than erroring, which is worse than a hard failure. Verified: all four casings store as `'free'` with price NULL, `"LIKE_NEW"` stores as `'like_new'`. Full-text **search** needed no change — Postgres `to_tsvector`/`plainto_tsquery` already normalize case; confirmed empirically that `free`/`FREE`/`FrEe` return identical results rather than assuming it.

- **Image-ownership verification failed on every request, including valid ones.** → `/api/listings` verified that each path in `images[]` was really an object the caller had uploaded by querying `storage.objects` via `supabase.schema('storage').from('objects')`. PostgREST does not expose the `storage` schema on this project, so that call returns `Invalid schema: storage` for *every* request. The check therefore never evaluated: malicious paths were rejected with a 500 instead of a 400 (fails closed, so not a security hole), but a legitimate listing with photos would have hit the same 500 — the happy path was broken. Caught by testing the "own prefix but never uploaded" case and noticing the status was 500 rather than the expected 400. → Switched to the Storage API: `storage.from(bucket).info(path)` per image (bounded at 5 by `MAX_LISTING_IMAGES`), which returns an `Object not found` error for a path that was never uploaded. Re-verified all four rejection cases return 400 and that a real photo upload now succeeds end to end.
- **Northeastern showed `launched_at = 2026-07-10` despite never having launched.** → `supabase/seed.ts` set `launched_at: new Date().toISOString()` when upserting active schools, so the column recorded when the seed script ran rather than when students got access — the site was still a teaser page on that date, and remains so. Spotted by the founder while reviewing the two-school setup ("I thought both schools launch Sept 5th?"). Harmless today, but it would have silently misreported launch dates in expansion analysis, cohort comparisons between the two schools, or any "live since" copy — the kind of wrong number that gets trusted because it looks precise. → Removed the assignment from `seed.ts` (re-running the seed no longer reintroduces it) and set the existing row back to NULL. Both schools now have `launched_at IS NULL`; it gets stamped at the real launch, i.e. the `NEXT_PUBLIC_LAUNCHED` flip. Note `active` and `launched_at` are orthogonal: `active` controls whether a school appears in the browse switcher, `launched_at` is a historical record.

- **NOT A BUG — logged only to correct the record.** The founder's `users` profile row vanished mid-session and was briefly treated as unexplained data loss. It was actually deleted deliberately by the founder, to re-test the sign-up → verification → sign-in flow now that Resend sending is properly configured (the original account predates working email, so its verification message was never sent). Claude "restored" the row from earlier session values, which undid that intent; the restore was then reverted. No data was lost and nothing in the test scripts deleted it. Real lesson: before treating missing data as an incident, ask — and don't re-create rows in a shared database on the assumption that their absence is accidental.

- **Free listings disappeared from the "Under $X" price filters.** → Both price-ceiling paths compared `price <= n` against a NULL price (NULL means free, per the schema's price rules). In SQL three-valued logic `NULL <= 50` evaluates to NULL, not true, so free items were silently dropped from every price bucket — the cheapest items in the feed were invisible under the filter most likely to surface them. Two separate code paths had the same bug: the browse query's `.lte('price', max)` in `lib/listings.ts` and the `search_listings` RPC from migration 010. → Migration `011_free_items_in_price_buckets.sql` adds `OR l.price IS NULL` to the RPC's ceiling condition; `lib/listings.ts` switched to `.or('price.lte.N,price.is.null')`. The separate free-items toggle is unaffected — it still narrows to only free items. Verified live on both paths (plain filter and filter+search) with seeded data: "Under $50" now returns the $15 item AND the free item while still excluding a $220 item.

## 2026-08-03

- **Supabase project subdomain stopped resolving (`NXDOMAIN`), blocking all API access.** → Free-tier Supabase projects auto-pause after a period of inactivity; the project had paused since the last session. Confirmed via `dig` (no records, even against 8.8.8.8 directly) while `supabase.com` itself resolved fine, and `supabase projects list` showed status `COMING_UP`. → Not a code issue. Resolved itself once the project finished resuming (polled `supabase projects list` until `ACTIVE_HEALTHY`, then confirmed DNS/API reachability directly).
- **Signing in with an unverified test account always failed with a generic "Incorrect email or password."** → Turned out to be Supabase's "Confirm email" project setting: with it enabled, GoTrue rejects sign-in entirely for any unconfirmed account (`email_not_confirmed`), and even a fresh `signUp()` call returned no session at all. This meant the "browse freely while unverified" UX from `CLAUDE.md` was unreachable under Supabase's default confirmation gate — not fixable in application code. → See `info/DECISIONS.md` ("Own email verification system") for the full resolution: disabled Supabase's confirm-email gate project-wide and built a separate, custom verified/unverified flag instead.
- **`supabase config push` failed with `unexpected status 402: Please upgrade the project to a paid tier to enable vector buckets`.** → The freshly-generated default `supabase/config.toml` (from `supabase init`) had `[storage.vector] enabled = true`, a Pro-tier-only feature, unrelated to the auth change actually being pushed. The Auth service config had already applied successfully before Storage failed. → Set `enabled = false` to match the actual (free-tier) remote state; push completed cleanly on retry.
- **Every email failure in the app was silent — `try/catch` around Resend never fired.** → Resend's SDK reports API failures (unverified domain, invalid key, rate limit) as a returned `{ data: null, error }` value rather than a thrown exception, so `try { await send() } catch {}` never caught anything. Two distinct consequences: (a) in `/api/waitlist` and `/api/auth/sign-up` a failed send was completely invisible — nothing logged, request returned success; (b) worse, in `/api/auth/resend-verification` and `/api/account/add-school-email` — whose *entire purpose* is sending an email — the routes returned `{success: true}` and the UI told the user "Check your email for a verification link" when nothing had been sent, leaving them waiting on an email that would never arrive. This is the root cause of the "signed up for the waitlist but got no email" report, which at the time was misattributed to missing Vercel env vars. → Centralized a `send()` helper in `lib/resend.ts` that converts Resend's returned `error` into a real thrown `Error`, making every existing `try/catch` correct. Added `waitlist.confirmation_sent_at` and `email_verifications.sent_at` (migration 007) set *only* on confirmed success, so failed sends stay `NULL` and are findable/retryable. Routes now split by intent: waitlist/sign-up log loudly but still return success (the row/account genuinely exists — failing would strand the user, and a sign-up retry would hit "email already exists"), while resend-verification/add-school-email return an honest 500. Both upsert routes explicitly reset `sent_at: null` so a stale timestamp from an earlier successful send can't survive an upsert and mask a new failure. Verified by running a second dev server with a deliberately invalid `RESEND_API_KEY`: waitlist returned 200 with `confirmation_sent_at` NULL and a logged `Resend send failed (validation_error): API key is invalid`; add-school-email returned a real 500 with `sent_at` NULL.
- **Email verification banner never appeared after sign-up, even though the session cookie was set correctly.** → `EmailVerificationBanner` was a client component using the browser Supabase client's `onAuthStateChange`. Sign-up happens via a *separate* server-side Supabase client (in the API route) that sets the session cookie directly in the HTTP response — the browser client instance never gets told that happened, since `onAuthStateChange` only reacts to auth actions taken through that same instance, not to cookies changed by an unrelated server response. `router.refresh()` after sign-up doesn't remount already-mounted client components either, so the banner's stale "no session" state from initial page load never updated. → Converted the banner to an async Server Component that reads cookies directly via the server Supabase client — correctly reflects fresh state on every `router.refresh()`, since that re-renders the Server Component tree (including layouts) with current cookies.
